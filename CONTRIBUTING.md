# Contributing

Thanks for helping. The goal is plugins whose advice is specific, faithful to the source and cheap on context.

## Ground rules

1. **Faithful to the source.** Components apply the upstream rule sets in `skills/principles/references/full.md`. Preserve modal strength (MUST / SHOULD / avoid). Do not invent rules.
2. **No book text.** Paraphrase and use original examples. Do not paste passages from the books or from Refactoring.Guru.
3. **One job per component.** If a new component overlaps a sibling, improve the sibling instead.
4. **Cite sources.** Every component ends with a `## Source` section naming the upstream headings it applies, in backticks, exactly as spelled upstream.
5. **Keep context cheap.** Only workflow-style skills may use `disable-model-invocation: true` to stay out of context; at most 20 skills per plugin may be model-invocable.

## Workflow

```bash
git checkout -b improve-<plugin>-<topic>
# edit plugins/<slug>/...
node scripts/gen-catalog.mjs
node scripts/build-targets.mjs     # regenerates dist/ for Codex, OpenCode, Gemini, MCP and the rest
node scripts/validate-all.mjs
```

All three commands must succeed before you open a pull request. CI repeats them and fails if generated files, including `dist/`, are not committed. Never edit `dist/` by hand: change `plugins/` and rebuild.

## Changing a component

- Edit the component, then regenerate: `node scripts/gen-catalog.mjs plugins/<slug>` and `node scripts/build-targets.mjs` (the build for the other agents; `validate-all.mjs` does not notice a stale `dist/`, but CI rebuilds it and fails on any difference).
- Bump the plugin `version` in `.claude-plugin/plugin.json` (patch for wording, minor for new components, major for renamed or removed ones) and add a line to the plugin `CHANGELOG.md`.
- Keep `docs/DESIGN.md` in step if you add, remove or merge components.

## Evals, settings and the review plumbing

- **Eval cases** live in `evals/<slug>/<case>/` and are described in [evals/README.md](evals/README.md). Plant five to seven violations the plugin's own rules name, one `llm` grader each; make the control clean by the book's rules. `node scripts/validate-evals.mjs <slug>` checks the structure without a model; `node scripts/run-evals.mjs <slug>` runs it and spends model usage. Commit the summary (`evals/summary/<slug>.json`) and `node scripts/summarize-evals.mjs` for `docs/EVALS.md`.
- **The project-settings and JSON-output text** inside the books is inserted by `node scripts/apply-project-settings.mjs`. Change the text in that script, run it, then bump the plugins. Do not hand-edit the marked blocks.
- **The `guided` plugin** is hand-written in `meta/guided/skills/*/SKILL.md`; its references and the preset bundles are generated by `node scripts/gen-guided.mjs`. Presets live in `scripts/presets.json` and may only combine books rated Complementary.
- **The CI runner, hook and Action** are tested by `node scripts/selftest-ci.mjs`. If you change what `claude` is asked or what it returns, run one real review with `scripts/guided-review-ci.mjs` as well: the stand-in cannot tell you the CLI changed.

## Adding a book

1. Add an entry to `scripts/books.json`.
2. `node scripts/new-plugin.mjs <slug> --upstream <clone of ciembor/agent-rules-books>`
3. Follow [docs/PLUGIN_SPEC.md](docs/PLUGIN_SPEC.md) section by section; the templates are in [docs/templates](docs/templates).
4. `node scripts/apply-project-settings.mjs && node scripts/gen-core.mjs && node scripts/gen-guided.mjs`, add an eval suite under `evals/<slug>/` (and a preset if it fits one)
5. `node scripts/gen-catalog.mjs && node scripts/build-targets.mjs && node scripts/validate-all.mjs`

## Reporting inaccuracies

Use the "Rule accuracy" issue template and cite the upstream section and what the component says versus what the source says.
